# Architecture

How the code is organised today, and what must not change by accident. For framework gotchas (Next 16, Tailwind v4, pdfjs, sharp) see `docs/STACK_NOTES.md`. `docs/PLAN.md` is the original plan and is historical.

The site is live. The owner is not a developer, so a change that alters stored data, the printed PDF or visible Arabic text has no reviewer but the tests: read "Hard invariants" at the end before any refactor.

API (`src/app/api`):

| Method and URL | Purpose |
|---|---|
| `POST /api/upload/direct` | Step 1 of an upload. Returns a one-time signed PUT URL, or `mode: 'server'` when the storage is the local disk. In-memory limit 20/h per IP (`limiters().upload`, shared with the multipart route). |
| `POST /api/upload/direct/commit` | Step 2. The server reads the stored bytes back, checks size and magic bytes and, for a PNG or JPEG, the image header (`rasterHeaderOk` in `src/app/api/_lib/image-header.ts`: sharp must read it and `width x height` must be within `MAX_INPUT_PIXELS`, 150 MP, from `src/lib/design/pixel-cap.ts`; a failure is `corrupt`, 400, and the file is deleted), then writes the meta file. The same `checkUploadBytes` also applies the per-file security rules of `src/app/api/_lib/file-safety.ts` (see `POST /api/upload`). Its own in-memory limiter, `limiters().commit` (40/h per IP, checked before the body is read; `rate_limited` + `Retry-After`), kept apart from the start's so one real upload does not spend two hits of one allowance. An id that already has a meta file is answered from the meta alone through the optional adapter method `uploadInfo(id)` (`{ meta, size }`, null when the meta or the .bin is missing: Supabase reads the .json and the .bin's object info, local stats the file; the kind comes from `kindForMime(meta.mime)`), so a retry never downloads the file; an adapter without `uploadInfo` falls back to `readUpload`. |
| `POST /api/upload` | Multipart upload for local storage. Same checks, all inside `checkUploadBytes` (`src/app/api/_lib/image-header.ts`, rules in `file-safety.ts`): a PNG needs the full 8-byte signature (else `unsupported_type`; `sniffKind` is golden-pinned and reads 4 bytes); a PNG or JPEG whose header does not decode, is over the pixel cap or has a side over 60 000 px is `corrupt`; a bounded decode (shrunk to 256 px, `failOn: 'error'`) must succeed, except that a PNG with a whole chunk stream (every CRC ok, IEND present) but too little pixel data is still accepted, because the golden route fixtures are such files (the order flow rejects it later); a PDF that pdf-lib can load (`ignoreEncryption`) is walked (max 200 000 objects, depth 64, past the bound it is accepted) and refused as `unsafe` (422, `order.errors.unsafe`) when a dictionary has /JS, /JavaScript, /EmbeddedFiles or /XFA, an /S of JavaScript, Launch, ImportData or SubmitForm, or a /Subtype of RichMedia, FileAttachment, Movie, Sound or Screen. A PDF pdf-lib cannot load is never rejected here (needs_raster / encrypted are handled later). `cleanOriginalName` also drops DEL, C1 and bidi controls. A rejected direct upload is deleted. |
| `POST /api/orders` | Creates the order (section 2). When the order's `uploadId` is an AI design, the generation is marked as ordered (`aiMarkOrdered`, best effort). |
| `POST /api/design/brief` | AI designer, step 1 (like step 2, it first refuses a body not declared `application/json` with 415 and a request whose `Origin` host is not the request's host with 403, both `invalid_request`; `app/api/_lib/same-origin.ts`): the customer's idea (which may also carry design instructions: colours, font, where the text goes) → the lines to print (spelling fixed), the fixes, an English artwork description signed with `briefToken` (HMAC of `SESSION_SECRET`), and, appended after the older keys, `instructions` (the same description in Arabic, for the customer to read and edit) with its `instructionsToken`. Limits: in-memory 30/h per IP, then the stored daily counter (`AI_BRIEF_PER_IP`, `AI_BRIEF_SITE`). Logic in `src/lib/ai/service.ts`. |
| `POST /api/design/generate` | AI designer, step 2: one image from the fixed prompt template, the signed description and the confirmed lines (the raw idea is stored, never sent to OpenAI). An optional `instructions` (at most 600 characters) with its `instructionsToken` comes back from the review box; edited instructions are translated to English after the reservation (see "Design instructions"). Checks in order: content type and origin (415 / 403), body, `briefToken`, 3:1 aspect, `settings.ai.enabled` + key, the in-memory `generate` limiter (15/h per IP, every attempt counts, never refunded; `ip_limit` + `Retry-After`), reference images (PNG/JPEG uploads; a read-only cap look and each one's meta first, then the bytes in parallel), the time left before its 110 s deadline (under 20 s for OpenAI: `failed`, nothing reserved; `maxDuration` 120), then the atomic daily reservation (`aiReserve`; blocked, site cap, per-IP cap). A failure after the reservation gives it back (OpenAI error, no time left once the reservation is done, undecodable image, PNG over 3.2 MB after maximum compression, save failure), except a custom image with no usable transparency: OpenAI charged for it, so the use is kept and the answer is `refused`. In production with `SESSION_SECRET` blank both routes answer `unavailable`. The PNG is stored as an ordinary upload and returned as base64. |
| `POST /api/team/design/brief`, `POST /api/team/design/generate` | Staff twins of the two routes above (`app/api/team/design/*/route.ts`): the same body, answers and capped body read (`handleAiPost`), `maxDuration` 120 on generate, but `staffApiGuard()` is the first statement (no valid `sf_staff` session: 401 `{ ok: false, error: "unauthorized" }`) and they call `runBrief` / `runGenerate` with `staffActor(staff.id)`. Counted per account, not per IP (see "Limits"). |
| `POST /api/team/upload`, `POST /api/team/upload/direct`, `POST /api/team/upload/direct/commit` | Staff twins of the three upload routes, for the reference images on `/team`. They share the handlers in `app/api/_lib/upload-handlers.ts` with the customer routes (same byte checks and file-safety rules), behind `staffApiGuard()` and the per-account limiters `staffUpload` (60/h) and `staffCommit` (120/h), and send no analytics `upload` event. |
| `POST /api/track` | Analytics beacon (section 5). |

Server actions (`src/app/admin/actions.ts`): `loginAction`, `logoutAction`, `updateOrderStatus`, `saveSettingsAction`; and `blockIpAction`, `unblockIpAction` in `src/app/admin/designs/actions.ts` (both start with `requireAdmin()` and accept only a 64-hex IP key). Staff designer: `staffLoginAction`, `staffLogoutAction` in `src/app/team/actions.ts`; the staff-account actions in `src/app/admin/staff/actions.ts` (all `requireAdmin()` first).

Admin protection has two layers and both stay:

1. `src/proxy.ts` (Next 16's replacement for `middleware.ts`) guards `/admin/*` and `/api/admin/*`, except `/admin/login`. No valid cookie: pages redirect to the login page, API routes answer 401 JSON. (The same file also gates the staff page, below; its matcher has `/staff/:path*` and `/staff-sheets` for that.)
2. Every admin page behind the login and the guarded actions (`updateOrderStatus`, `saveSettingsAction`, `blockIpAction`, `unblockIpAction`) call `await requireAdmin()` (`src/lib/auth/guard.ts`) as their first statement, and every admin route handler calls `adminApiGuard()` (`src/lib/auth/session.ts`). The login page and the admin layout call `verifySession()` directly.

The session is an HS256 JWT (`src/lib/auth/token.ts`) in the HttpOnly cookie `ep_admin`, valid 7 days.

**Staff designer sessions (`/team`, added 2026-11-26)** are a third thing, separate from both the admin login and the secret staff link above (the names are close; the code is not shared):

- Cookie `sf_staff`: an HS256 JWT signed with `SESSION_SECRET` (at least 32 characters), claim `role: 'staff'`, `sub` = the staff account id, valid 7 days, `HttpOnly`, `SameSite=Lax`, `Secure` when `x-forwarded-proto` is https, path `/` (both `/team` and `/api/team` read it). `src/lib/auth/staff-token.ts` is proxy-safe like `token.ts` (no `server-only`, no `next/*`). Admin and staff tokens share the secret, so the `role` claim is the only separator: `token.ts` accepts only `admin`, `staff-token.ts` only `staff`. Staff logout (`staffLogoutAction`) moves the account's `passwordChangedAt` (the session cutoff) to now, so it ends that account's sessions on every device, like a disable or a password reset; admin logout only clears its own cookie.
- `src/lib/auth/staff-session.ts` (`server-only`): `createStaffSession`, `currentStaff()`, `requireStaff()` (pages: redirects to `/team/login`), `staffApiGuard()` (route handlers: `{ staff }` or the 401 JSON answer to return as is), `destroyStaffSession()`. `currentStaff()` re-reads the account on every call, so a disabled account is refused on its next request, and fails closed (a storage outage, a missing table or method means "nobody"). A token issued before the account's `passwordChangedAt` is refused, compared in whole seconds (a password reset logs that account out everywhere; a login in the same second as the reset still works).
- Passwords (`src/lib/auth/password.ts`, `server-only`): `scrypt` from `node:crypto`, no dependency. A random 16-byte salt per password, stored as `scrypt$N$r$p$saltB64$hashB64` (N 16384, r 8, p 1, 32-byte key, `timingSafeEqual`). Input is NFC-normalised and Arabic-Indic digits become Western, so a password typed on a phone keyboard matches. Minimum 8 characters (`STAFF_PASSWORD_MIN`), `verifyPassword` never throws and refuses anything malformed. The login verifies against `dummyHash()` when the phone is unknown, so an unknown phone costs the same time as a wrong password.
- `staffLoginAction` answers one generic error for an unknown phone, a wrong password, a disabled account and a malformed form. Limits (in memory, `rate-limit.ts`): `staffLogin` 10 per 15 min per IP (kept apart from the admin `login`, so staff guessing never locks the admin out) and `staffLoginPhone` 10 per 15 min per normalised phone; both answer `?error=rate`.
- **No proxy coverage, by design (R3).** `src/proxy.ts` and its pinned matcher are unchanged: its `staffGate` takes every path that starts with `/staff`, and `/team` is deliberately not one of them. So the proxy does nothing for `/team` or `/api/team`; the protection is only in the code: every `/team` page behind the login starts with `await requireStaff()` and every `/api/team/*` handler with `staffApiGuard()`. A new `/team` page or route that forgets the guard is open to the world.

**The staff page** (`/staff/<key>`, added 2026-11-12) is NOT behind the admin login: it is a secret link, no password (owner decision D3). There is no `/staff/[key]` route: a page's own `notFound()` would answer with an error shell whose embedded route data names the route and echoes the key, which an unknown URL never does. Instead `src/proxy.ts` checks the key with `matchesStaffKey()` from `src/lib/staff-gate.ts` (constant time over sha256 digests, case-sensitive; a `STAFF_PAGE_KEY` shorter than 24 characters counts as "not set") and:
- right key: rewrites to the real route `/staff-sheets` (`STAFF_PAGE_ROUTE`), passes the key in the request header `x-staff-key` (`STAFF_KEY_HEADER`, always overwritten by the proxy) and adds the response headers `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex, nofollow`. They are set there, not in `next.config` `headers()`, because a config rule for `/staff/:path*` would also put them on the wrong-key 404 and make it differ from an unknown URL;
- any other `/staff` URL (wrong, missing or unset key, other letter case, extra segments): `NextResponse.next()`. No route matches it, so Next serves its normal 404 with the same bytes and headers as an unknown URL (checked against a production build). A proxy rewrite is not used here on purpose: Next copies every rewrite target into an `x-middleware-rewrite` response header;
- `/staff-sheets` asked for directly: rewritten to `/staff-sheets/not-found`, a path with no route, so it gets the same 404 page (it is the one URL whose answer also carries `x-middleware-rewrite`).

The page (`force-dynamic`) checks the key again with `isStaffKey()` from `src/lib/staff-key.ts` (`server-only`) on the request header and calls `notFound()` otherwise, as a second line of defence. It is `noindex, nofollow` and `no-referrer` in its metadata too, is absent from the sitemap and `robots.txt`, and is ignored by analytics (`src/lib/analytics/paths.ts` `isStaffPath`, in any letter case, used by `Tracker`, `/api/track` and `InstallPrompt`; the browser keeps the `/staff/<key>` URL, which is what `Tracker` sees), so the key never reaches the stats. The admin settings link is built by `src/app/admin/settings/staff-link.ts` from the first value of `x-forwarded-host` / `x-forwarded-proto`. The page changes no customer data and uploads nothing: the client component (`src/components/staff/StaffSheets.tsx`, with `StaffCard`, `useStaffItems` and the pure `staff-logic.ts`) decodes each design in the browser (`decodeDesign`), arranges it with the website's own layout engine (`layoutParamsFor`, so the same margin, gaps, rotation and dots), prepares the artwork (`prepareOriginalArtwork` in `src/lib/design/original.client.ts`, owner change 2026-11-26: the uploaded file's own bytes, so full resolution and original colours, CMYK included; a JPEG's EXIF turn is drawn as the raster artwork's optional `rotate`; header checks in `src/lib/design/image-header.ts`; files pdf-lib cannot embed as they are (mirrored EXIF, CMYK without the Adobe marker, wide-gamut ICC, APNG, custom-shape crop, huge PNG) go through `prepareArtwork` in `prepare.client.ts` at native resolution, never downscaled; PDFs stay the original PDF with the server's box and turn from `src/lib/design/pdf-box.ts`) and builds one PDF file per design, each with one A4 page (`buildStaffPdf([item], now)`, dynamically imported), prepared, built and saved one after another about 400 ms apart (`downloadStaffFiles` in `staff-logic.ts`; names from `staffPdfName`: `<design name>-<size>.pdf`, `-2`, `-3` for duplicates). A design that fails is reported and the others still download; each ready card also has its own download button. Owner change 2026-11-12: this replaced decision D1's single multi-page PDF. Limits: 30 files, 50 MB each. Copy is in `src/content/ar/staff.ts`. The owner changes the link only through the Vercel variable (then redeploys).

**Receipts tab (الوصولات, added 2026-11-26).** The staff page has two tabs (`StaffTabs.tsx`, base-ui Tabs, both panels kept mounted). The receipts tab (`src/components/staff/receipts/`: `StaffReceipts`, `ReceiptCard`, `useReceiptItems`, pure `receipt-logic.ts`) imposes one receipt design per card on one A4 page for receipt books: formats A4 / A5 / A6 / DL with the owner's slot table in `src/lib/receipts/formats.ts` (pinned by `tests/unit/receipts/formats.test.ts`; the white strip is the punch-and-binding edge), the design stretched to fill each slot, auto-turned a quarter counter-clockwise when its orientation differs from the slot's (the employee can turn further; A6 white top or bottom), format guessed from the file name (`10 a5 ….pdf`), the PDF page size or the aspect. The PDF (`src/lib/pdf/build-receipt-pdf.ts`, isomorphic, uses `embedArtwork` from sheet-page) has no cutter dots and no margin (guillotine cut). ## 2. Order pipeline

In the browser (`src/components/builder`): `useBuilder.ts` holds the step state, `src/lib/design/decode.client.ts` decodes the file for the preview, and `useSubmitOrder.ts` runs `submitFlow.ts` (the upload and order sequence, free of React) through `orderApi.ts` (the HTTP calls). The quantity step takes a STICKER count: `useBuilder` keeps what was typed (`null` = never typed, the box then shows the minimum for the current layout and follows it when the size changes), and derives sheets, the error (`validateStickers`) and the price (`priceForStickers`). The − / + buttons, quick picks and the discount chips/nudge are in stickers (`logic.ts`: `stepStickers`, `quickPickStickers`, `nextTierNudgeStickers`); the settings stay in sheets. The order in progress survives a reload and a closed tab, for 2 hours (`DRAFT_TTL_MS`, owner decision 2026-11-21; counted from the last change for the order and from the upload for the design file; `saveDraft` / `loadDraft` / `clearDraft` in `logic.ts`): the order (shape, size, quantity, `step`, `fileId`) goes to `localStorage` key `ub:draft:v1` as `{ v, savedAt, form }`, WITHOUT the customer's name, phone and address; the full form is mirrored to `sessionStorage` key `ub:form:v1` (what an older page wrote; it keeps the personal fields for this tab only, and is the fallback when `localStorage` is blocked). `loadDraft` merges the two. The form stores `stickersText` (an old `sheetsText` is ignored), `step` (optional; an old form without it opens the first step) and `fileId`. The uploaded design is stored as the original file in IndexedDB database `ub:draft`, one slot with its own `savedAt` and the `id` of the form it was saved for (`draft-store.ts`, every call best effort: without IndexedDB it does nothing). Tabs share `localStorage` and that one slot, so a stored file is restored only when its `id` equals the form's `fileId`; otherwise the design is dropped and the customer picks it again. After a reload `useBuilder` hides the page (`restoring`), feeds the stored file through the same `loadDesign` a fresh pick uses, with `keepSize` so the saved sizes are not overwritten, then opens the saved step clamped to `furthestStep` (what `canGoTo` allows). A restore that takes more than 10 s shows the page but goes on; anything the customer starts meanwhile (`cancelRestore`) ends it. A successful order clears the form, the draft and the file. The order id of a submit in flight is kept separately (`submitAttempt.ts`: pure helpers plus best-effort storage). `useSubmitOrder` fingerprints what defines the order (sticker spec, material, stickers, sheets, customer fields, design file name, size and `lastModified`, seed upload id; never the rasterised JPG of the `needs_raster` path) and keeps the same `orderId` for a retry of the SAME order, also after a reload, through `sessionStorage` key `ub:order-attempt:v1` as `{ v, orderId, fingerprint, savedAt, uploadId?, rastered? }` (24 h; the server's idempotency then returns the order it already saved instead of creating a second one). `uploadId` and `rastered` are optional (an older record has none) and are written as soon as an upload finishes (`rememberUpload`): the server replays a saved order only for the upload it was saved with, so a retry after a reload must send that same upload id (also the rasterised JPG of a PDF) and not upload the file again; such a reused upload is marked `seeded`, so if the server no longer has it the file is uploaded once more. A changed order gets a fresh id, and the finished upload is reused only when the design did not change (never a rasterised JPG). The key is cleared on success and on a fixable error; `rate_limited` keeps the attempt, because an earlier try with that id may have been saved.

1. **Start the upload.** `POST /api/upload/direct` with the file size and name. On Supabase the answer carries an upload id and a signed URL. On local storage it is `mode: 'server'` and the browser falls back to the multipart `POST /api/upload`.
2. **Send the file.** The browser PUTs it straight to the bucket (`uploads/<id>.bin`). Vercel caps request bodies at 4.5 MB, so the file never passes through a function.
3. **Commit.** `POST /api/upload/direct/commit`. The server reads the real bytes back, rejects empty, oversize, unknown or undecodable-header files (and deletes them), then writes `uploads/<id>.json`. `readUpload()` needs both files, so an unchecked file can never reach an order. A retry for an id that is already committed is answered from the meta (`uploadInfo`), without downloading the file. `uploadInfo` answers null for anything that is not a clean success (a 404, Storage's 400 with an inner 404, a 5xx, an unreadable body, no size), and a null is "unknown", not "missing": the commit then asks `readUpload`, which decides (and throws on a real outage, so that is still a 500). A thrown network error is not caught.
4. **Order.** `POST /api/orders` with `{ orderId, uploadId, spec, material, stickers, customer }` (`stickers` is the count the customer typed; pages cached before 2026-11-11 send `sheets` instead, and that path still works: see "Pricing" below). `orderId` is made by the browser and is the idempotency key: a repeat returns the stored result. The route, in this order:
   1. rate limit, before the body is read; body capped at 64 KiB; zod validation (`src/lib/order-schema.ts`); then `getSettings()`, then idempotency: an order already stored under this `orderId` is answered as is, but only when the request names the same upload (`existing.files.designPath === uploadPath(req.uploadId)`; a retry resends the whole body), otherwise the answer is `invalid_request`; a request still running for it is awaited (none of the checks below run again);
   2. Turnstile check, only when `TURNSTILE_SECRET_KEY` is set (it must not be, see section 4);
   3. phone normalisation, quantity validation, `readUpload`. With `stickers` the quantity is checked by `validateStickers` against a layout the route computes right there (pure, the same call as step 4); when that layout fails only the material is checked, so the layout error still comes at step 4. With `sheets` only, `validateQuantity` as before;
   4. **layout**: `computeLayout(spec, layoutParamsFor(spec, settings.layout))` (`src/lib/layout`);
   5. **normalise**: `normaliseArtwork` (`src/lib/design/normalise.server.ts`, sharp and pdf-lib; includes the DPI gate). **Print resolution is fixed at `PRINT_DPI` = 1200** (`src/lib/print-dpi.ts`, owner decision 2026-11-15), on the website (the staff page has used the original file since 2026-11-26, see "The staff page"): it is a maximum, so a raster sharper than 1200 DPI at the ordered size is resampled DOWN to exactly 1200, a raster below it is kept as is (never upscaled), a vector PDF stays vector. `settings.quality.targetDpi` is deprecated and ignored (kept only so stored settings still parse). The browser's PDF fallback (`rasterisePdfPage`) and `prepareRaster` keep every canvas under `MAX_CANVAS_PIXELS` (`src/lib/design/pixels.ts`; iOS Safari refuses more): the PDF is rendered at the ordered size and, if even that is too big, at a lower DPI; the final raster canvas is made at full size and only retried one size down (`fitToPixelCap`) when the browser refuses it;
   6. **PDF**: `buildSheetPdf` (`src/lib/pdf/build-sheet.ts`);
   7. price: `priceForStickers` (or `priceFor` for a sheets-only request) on the server. The browser never sends a price, and a request with `stickers` never uses the client's `sheets`;
   8. **save**: `savePdf`, then `saveOrder` with the record built by `src/lib/order-record.ts`. `saveOrder` is first-write-wins and cannot say it lost, so the order is read back (`getOrder`, one extra GET): when the stored record has another `displayNo`, a retry on another serverless instance got there first, and this run answers with that record and stops (no AI mark, customer upsert, event, Telegram or `updateOrder`; the PDF it wrote may have replaced the winner's, same inputs, only the PDF title differs). A failed read-back counts as a win (a second message beats a lost one). When `saveOrder` itself throws (the 10 s abort can fire after the insert committed) the order is read back as well: ours means carry on, someone else's means answer with it, absent means `server_error`;
   9. **customer upsert**: `upsertCustomerFromOrder`, which also records the WhatsApp-offers choice (section 5; best effort; a failure logs a fixed message with a short code, never the error text, and goes to Sentry);
   10. **analytics**: an `order` event (best effort);
   11. **notify**: `notifyShop` (`src/lib/notify`): Telegram `sendDocument` with the PDF, or a console log (on Vercel, `VERCEL=1`, the line is `[order] <file> (<n> bytes) <displayNo>` with no caption, so no phone or address reaches the platform log; elsewhere the full caption is logged). It never throws. The result is stored on the order as `notified`.
5. **Answer.** `{ ok: true, orderId, displayNo, summary, whatsappUrl, notified }`. The browser stores it in `sessionStorage` and opens `/order/success`.

Failures are `{ ok: false, error, message }` with the status from the table in the route. Two are handled specially by the browser: `needs_raster` (it renders the PDF page to a PNG, uploads that and retries once) and `server_error` or a network failure (it shows the "degraded" screen with a ready WhatsApp message built by `degraded.ts`).

**Cutter dots (sheet marks).** The camera cutter reads only the printed paper and finds the sheet by 4 black dots (owner decisions, 2026-11-12). Every sheet PDF carries them: customer orders and the staff page. The geometry is fixed in code (`REG_MARKS` in `src/lib/layout/marks.ts`), not a setting: dot diameter 5 mm, centre 7 mm from both nearest edges (TL (7,7), TR (203,7), BL (7,290), BR (203,290) mm), no printed part of a sticker within 3 mm of a dot's edge (keep-out radius 5.5 mm around each centre). `layoutParamsFor()` always passes `marks`, so the website builder, `POST /api/orders`, `/how-it-works` and the staff page share one rule. `computeLayout` without `params.marks` behaves exactly as before (`layout-cases.json` is never edited; mark cases live in their own fixtures). With `marks` the engine searches three candidate areas (the usable area, then the area with the left and right edges, or the top and bottom, moved in to clear the dots), removes placements near a dot, and keeps the arrangement with the most stickers after removal (`LayoutResult.marks`, `removedNearMarks`; `countPerSheet` and `turnedCount` are counted after removal). For circle clips the printed shape is the inscribed circle; for every other shape the whole cell. The default margin is 3 mm (`DEFAULT_SETTINGS.layout.marginUm = 3000`). In the PDF the dots are one path (4 circles, `f*`) in DeviceCMYK `0 0 0 1`, inside the optional-content layer `sk_marks`, copied from the shop's hand-made `example.pdf`; rounded rectangles are clipped to their rounded corners (the camera cuts what is printed); the document asks viewers not to scale when printing (`/ViewerPreferences /PrintScaling /None`). `drawCount` still counts artwork draws only. The preview (`SheetPreview`, `SheetIllustration`) draws the dots in black and shows `common.marksHint`.

**Pricing** (`src/lib/pricing.ts`, pure, shared by the builder and the route; owner rules of 2026-11-10 and 2026-11-11):

- The customer types a sticker count. `sheets = ceil(stickers / countPerSheet)` (`sheetsForStickers`); the customer receives the whole last sheet (`totalStickers = sheets × countPerSheet`). Allowed range: `minStickers` = `pricing.minSheets × countPerSheet` to `maxStickers` = `pricing.maxSheets × countPerSheet`, whole numbers only (`validateStickers`). A count per sheet ≤ 0 never divides: it gives 0 sheets and `below_min`.
- Per-sheet price, volume tiers and quick picks stay in SHEETS in the settings; the tier is chosen on the rounded-up sheet count.
- `raw = unitPrice × sheets + delivery`; `totalIqd = max(delivery, raw rounded to the nearest PRICE_ROUND_IQD = 1,000, halves up)`; `subtotalIqd = totalIqd − delivery`; `roundingIqd = totalIqd − raw` (may be negative). `perStickerIqd = round(totalIqd / totalStickers)`. Unpublished prices: every money field null. The step is a constant in `pricing.ts`, not a setting.
- The typed count is stored as `price.requestedStickers` and returned as `summary.requestedStickers`; the Telegram caption, the WhatsApp text and the admin order page show it as «العدد المطلوب». Orders saved before 2026-11-11 have neither `requestedStickers` nor `roundingIqd` and their totals are not rounded; every screen handles that.

The order of steps 8 to 11 is deliberate: the PDF is saved before the order, the order before the notification, and the three side effects run one after another.

## 5. Analytics: privacy model and retention

First-party and cookieless. Events: `pageview` (sent by `src/components/shell/Tracker.tsx`), `step` (once per builder step per browser session), `install` (the install card), and the server-side `upload` and `order`. The browser part is `src/lib/analytics/client.ts`, the server part `src/lib/analytics/server.ts`.

- **Stored per event:** time, type, visitor hash, path, step, traffic source, device class, city, region and country (from Vercel's `x-vercel-ip-*` headers, absent locally) and a small `meta` object (for an order: material, sheets, the typed sticker count when there is one, total, governorate, shape, size).
- **Never stored:** IP address, user agent, the referrer URL (it is reduced to a source name such as `instagram`), cookies, names or phone numbers.
- **The one exception is not analytics.** The AI designer tables (`ai_usage`, `ai_generations`, `ai_blocks`) store the **full client IP** next to a keyed hash (`ip_key`, below). This is an explicit owner decision (D9, 2026-11-21): the admin page must show which address hit the limit and let the owner block it. It applies to those three tables only. Analytics events, Sentry and logs still never carry an IP.
- **`ip_key`** is `HMAC-SHA256(SESSION_SECRET, "ai-ip|" + ip)` in hex (`src/lib/ai/ip.ts`, `aiIpKey`). It is the limit and block key, so a block survives the IP text being formatted differently. For a customer the `ip` hashed is `aiLimitAddress(ip)`: an IPv4 address as it is, an IPv6 address as its /64 (`2001:db8:1:2::/64`), so one device cannot get a fresh allowance by changing its address inside its own network; the stored and displayed IP stays the full address. When `clientIp()` answers `global` (`TRUST_PROXY=0`, local development) the key is empty: the per-IP limit is skipped and only the site cap applies. `ipOf()` (analytics) and `clientIp()` (rate limits) stay separate (invariant 9).
- **Visitor hash:** the first 16 hex characters of `sha256(shop day | IP | user agent | salt)`. It changes every day, so one visitor cannot be followed across days. The salt is `SESSION_SECRET`: changing that secret splits the same day's visitors in two.
- **Dropped:** bots, an empty user agent, every `/admin`, `/staff` and `/team` path in any letter case (`isAdminPath`, `isStaffPath`, which also covers `isTeamPath`), anything beyond 300 events per hour from one visitor hash, and anything beyond 600 per hour from one address (`limiters().trackIp`, keyed by `clientIp()` as a limiter key only, nothing new is stored; checked first, because the visitor hash changes with every User-Agent string; x20 without `TRUST_PROXY` like the other per-address limiters; a carrier-NAT address may lose some real events). `/api/track` answers 204 whether it stored the event or not (400 only for an invalid body).

Retention:

| Data | Kept for | Removed by |
|---|---|---|
| Sheet PDFs (`orders/<id>.pdf`) | `settings.retentionDays` (default 30; the admin label says it is the print file) | `GET /api/cron/purge` daily on Vercel; `pnpm purge:orders` locally. The PDF can be rebuilt, so it is the only large file that goes. |
| Orders (record) and their design file | **forever** (owner decision D10, 2026-11-21), so a future "order again" can reuse them | never. **Exception:** orders created before `KEEP_DESIGNS_FROM` (`src/config/defaults.ts`; set it to the deploy date in the deploy commit) keep the old rule: record, PDF and design removed after `retentionDays`, as those customers were told |
| Generated designs (`ai_generations` rows and their upload files) **an order used** (`order_id` set, whatever the order's status) | forever (D10) | never: the purge skips every upload that an order points to |
| Generated designs **no order used** (customer and staff alike) | **7 days** (`UNORDERED_DESIGN_DAYS`, owner 2026-11-26) from `created_at`; supersedes "forever" of D10 for these | the cron: `aiPurgeUnordered(now − 7 days)` removes the upload (`.bin` + `.json`) and then the row. Before deleting it reads every order created since the oldest candidate − 1 day and **heals** (sets `order_id` on) a design an order does use instead of deleting it; any read failure throws and nothing is deleted. A row whose files could not be deleted stays and is retried the next day. Details below. |
| Plain uploads (no generation) that no order and no remaining generation uses | 7 days from creation (before 2026-11-26: `retentionDays`) | the cron: `purgeUnusedUploads(now − 7 days)`, run after the step above, within `[cutoff − PURGE_WINDOW_DAYS, cutoff)` (plain uploads older than the window are not swept). `purgeOlderThan` still removes unused uploads at `retentionDays`; the 7-day step simply gets there first. |
| Direct uploads never committed (no meta file) | 3 hours | the cron |
| Blocked IPs (`ai_blocks`) | forever | the admin's «إلغاء الحظر» |
| Staff accounts (`staff_accounts`) | forever; never hard-deleted (generations point at them), only disabled | never |
| AI daily counters (`ai_usage`) | 400 days (`AI_USAGE_RETENTION_DAYS` in `src/app/api/cron/purge/route.ts`, the same as analytics events). A few rows per IP per day. The admin page reads only this month and yesterday from them for its today, month and alert counters; its all-time counter counts `ai_generations` rows, so it does not shrink when old usage rows go. The daily limits only need today's rows | the cron on Supabase (`?dry=1` counts only); the local script (`pnpm purge:orders`) does not remove them |
| Analytics events | 400 days | the cron (the local script does not remove them) |
| Customers | permanently (owner decision; the consent text says so). Includes the optional WhatsApp-offers opt-in (below) | never |

**WhatsApp-offers opt-in (2026-11-21, owner request).** The delivery step has one checkbox, «ابعثولي عروض وخصومات على الواتساب (اختياري)», unticked by default and separate from the consent sentence (which is unchanged). It is session-only React state in `useBuilder` (`marketingOptIn`), deliberately outside `FormFields`: it is never written to the `ub:draft:v1` draft or to sessionStorage, so it can never come back pre-ticked, and it is false on every fresh page. The request carries `customer.marketingOptIn` (zod `boolean`, optional, no default, so an unticked order parses exactly as before; the page sends the key only when ticked; every reader tests `=== true`). `buildOrderRecord` stores `customer.marketingOptIn: true` and `customer.marketingOptInAt` (= the order's `createdAt`) only for an opt-in, appended after `notes`, so every other order keeps its exact old shape. `CustomerRecord.marketingOptIn` / `marketingOptInAt` follow one rule: **the latest order's explicit choice wins**. An order without the box ticked withdraws a stored yes (`marketingOptIn: false`, `marketingOptInAt: null`); `marketingOptInAt` is the time of the latest opt-in. An older order that arrives late never overrides a newer choice (same `createdAt >= lastOrderAt` test as `lastOrderId`). A customer who never ticked has no opt-in keys at all (local) / `marketing_opt_in = false` (Supabase). An old cached page that does not send the key counts as unticked. In Supabase the rule lives in `upsert_customer_v2` (migration `20261122000000_marketing_opt_in.sql`, columns `marketing_opt_in boolean not null default false` and `marketing_opt_in_at timestamptz`, executable by `service_role` only); `SupabaseStorage.upsertCustomerFromOrder` calls it and, when PostgREST answers 404 (function missing, migration not applied), logs once and falls back to the old `upsert_customer` so the customer is still recorded. `/admin/customers` shows a «عروض واتساب» badge and a «واتساب عروض» filter; `GET /api/admin/customers` adds two columns at the END of the CSV (opt-in نعم/لا, opt-in date) and `?marketing=1` exports only opted-in customers («تنزيل قائمة العروض»). The box is left out of the order-attempt fingerprint (`attemptFingerprint`), because it is not restored after a reload: ticking it never changes the order id, and a replayed order keeps the choice it was first saved with. Nothing sends marketing messages: the list is for the owner to use by hand, and only for customers whose latest order ticked the box.

**The 7-day rule (2026-11-26) in detail.** `aiPurgeUnordered(cutoff = now − 7 days)`: candidates are `ai_generations` rows with `order_id` null and `created_at < cutoff`, with NO lower bound (paged, stable order, at most 1000 per run on Supabase, oldest first; the rest follows the next day). Each candidate is re-verified in code (null `order_id`, date before the cutoff, plain ids). Orders created since (oldest candidate − 1 day) are read before anything is deleted (an order is always created after the upload it uses) and once more right before the deletes; a candidate whose upload is the `designPath` or any `designPaths` entry of an order is healed with `aiMarkOrdered` and never deleted, even if the heal itself did nothing. Then, per chunk of 100: the explicit upload paths (`.bin` + `.json`) are removed first and the rows after, by `id=in.(…)` with `order_id=is.null&created_at=lt.<cutoff>` as backstops (never a date-range delete); a chunk whose file deletion fails keeps its rows and the run throws (the cron reports it), so tomorrow retries. `purgeUnusedUploads` runs second, so the uploads of the designs just removed are not "used" by anything; it reads orders and generations since one day before the window start. Known limits: an order placed between the safety reads and the deletes (seconds) is not seen (the second read narrows this); plain uploads older than `cutoff − 30 days` on the first run are outside the window and stay. Run `GET /api/cron/purge?dry=1` on live before the first real run and look at `removedDesigns` / `removedUploads`. `aiDeleteGeneration(id)` deletes one gallery row by exact id and never touches files; `orderUsingUpload(uploadId)` finds the order that uses an upload (any age, fail closed).

Every purge run deletes print PDFs of kept orders and unused uploads only in `[cutoff − PURGE_WINDOW_DAYS (30), cutoff)`, and a cron that stops for more than 30 days leaves those items of the skipped days behind (they are not picked up later). Old-rule orders (created before `min(cutoff, KEEP_DESIGNS_FROM)`) have **no lower bound**: every one still there is removed with its PDF and design, so an outage or a lower `retentionDays` never strands a promised deletion (that set only holds what is left from before the switch). An old-rule design that a kept order still uses stays (when `KEEP_DESIGNS_FROM` lies before the reference read, Supabase asks for such a design by path first). What is read is wider than what is deleted: the Supabase adapter also reads every order and every `ai_generations` row created since one day before the window start (no upper bound, to learn which uploads and designs are still in use), every old-rule order, and lists `uploads/` and `orders/` newest first back to the window start, so one run costs roughly the activity of the last `retentionDays + 31` days (plus the shrinking old-rule leftovers) and grows with order volume in that span, not with all history. The local adapter reads every order file (`listOrders`). `aiPurgeUsageBefore` and the events purge are separate, whole-table deletes. The deletion promise was removed from the site copy (D11): `builder.details.consent` and `common.filesNotice` no longer say that design files are deleted after a period, because designs an order used are kept (since 2026-11-26 designs no order used go after 7 days, an OWNER decision still open for the site copy: the copy does not say so yet); the sentences about keeping the customer's name, phone and address stay.

## Meta Pixel and Conversions API (ads)

**Events.** `PageView` on every route; `ViewContent` when the builder shows the `design` step, `AddToCart` at `quantity`, `InitiateCheckout` at `details` (`META_STEP_EVENTS`; sent from `useTrackStepOnce` in `useBuilder.ts`, so once per step per browser session, like the `step` event); `Purchase` twice for one order: from the success page (`trackMetaPurchase`, once per order per tab through `sessionStorage` key `meta-purchase:<orderId>`) and from the server (`sendMetaPurchase`, new orders only: a replay or a lost race returns before it). Both copies carry `eventID` / `event_id` = the order id, so Meta deduplicates them and counts one purchase. The value is `totalIqd / NEXT_PUBLIC_META_IQD_PER_USD` in USD (2 decimals) or nothing at all: never a made-up number (no rate set, prices unpublished, or a null total).

**Never on private paths.** `isMetaExcludedPath` (`isAdminPath` or `isStaffPath`, any letter case) is checked before the script is even loaded and again before every event, so `/admin`, `/staff/<key>`, `/staff-sheets` and `/team` never load Meta's script and never reach Meta (invariant 20). `fbq.disablePushState = true` stops Meta from counting history changes on its own, and `autoConfig` is off, so it sends no automatic button-click or page-metadata events: only the events listed above.

**What the server sends** (`capiPurchaseBody`, unit-tested): `event_name: Purchase`, `event_time`, `event_id` = order id, `action_source: website`, `event_source_url` (the referring page of the same host without query or fragment, else the site root), `user_data` with the phone (`9647…`) and the country (`iq`) as SHA-256 hex as Meta requires, the IP (first `x-forwarded-for` entry, only when `net.isIP` accepts it) and user agent as they are, and the `_fbp` / `_fbc` cookies when they have Meta's format; `custom_data` with `order_id` and the value. Never the name, the address, the notes, the file or the phone in clear. The POST (`graph.facebook.com/v24.0/<pixel>/events`, `META_GRAPH_VERSION`, 5 s timeout, token in the JSON body) runs inside `after()`, so it never delays or fails an order; a refusal or a network error is reported to Sentry as a warning with the status code only (`orders.metaCapi`), never the answer body. Meta keeps a Graph API version for about two years: bump `META_GRAPH_VERSION` before it is retired.

**Setting it up** (owner): create the dataset in Events Manager (the business must accept Meta's pixel terms there), put its id in `NEXT_PUBLIC_META_PIXEL_ID`, generate a Conversions API access token in the dataset's settings and put it in `META_CAPI_TOKEN`, optionally set `NEXT_PUBLIC_META_IQD_PER_USD`, then **redeploy** (the two `NEXT_PUBLIC_` values are baked in at build time). To check, set `META_TEST_EVENT_CODE` to the code from Events Manager → Test events, place an order, see the browser and server `Purchase` arrive and merge, then clear the variable and redeploy.

## Security headers

`next.config.ts` sets `poweredByHeader: false` (no `X-Powered-By`) and one site-wide `headers()` rule, source `/:path*`: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` and `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()` (the site uses none of those features). The site is never meant to be framed. It is deliberately **only** `frame-ancestors`: no `script-src` or other CSP directive, because Next's inline scripts, Sentry and the pdfjs worker would need a nonce set-up that is not done. There is no `/staff`-scoped rule and no `Referrer-Policy` here: the rule is the same for every path, so a wrong `/staff/<key>` still gets exactly the unknown-URL answer (invariant 11), and `src/proxy.ts` keeps setting `Referrer-Policy: no-referrer` on the staff page. Check after a deploy: `curl -I` the home page and a wrong staff URL; both carry the four headers, and neither shows `X-Powered-By`.

## Error monitoring (Sentry)

`@sentry/nextjs` 11.x reports every error a customer hits, **errors only**: no performance tracing (`tracesSampleRate` is left unset on purpose, 0 would still create spans), no session replay, no profiling, no logs, no release-health sessions. With `NEXT_PUBLIC_SENTRY_DSN` unset (local development, tests, the live site until the owner sets it) every init is skipped and every capture call is a no-op.

| Piece | File |
|---|---|
| Browser init (errors, `tunnel: { path: '/monitoring' }`) | `src/instrumentation-client.ts` (no `onRouterTransitionStart`: it is a tracing hook) |
| Server init (Node.js runtime) and the tunnel answer | `src/sentry.server.config.ts`, loaded by `register()` in `src/instrumentation.ts` |
| Uncaught server errors (pages, route handlers, server actions, the proxy) | `export const onRequestError = Sentry.captureRequestError` in `src/instrumentation.ts` |
| Uncaught browser errors and unhandled rejections | the SDK's global handlers; a render crash lands in `src/app/global-error.tsx` |
| Build wrapper (source maps only when `SENTRY_AUTH_TOKEN` is set, deleted after upload, tracing code left out, no build-time instrumentation) | `next.config.ts` (`withSentryConfig` from `@sentry/nextjs/config`; the `nextConfig` object itself is unchanged) |
| Shared settings (`dataCollection`, tunnel path, DSN reader) | `src/lib/monitoring/config.ts` |
| The scrubber (pure, unit-tested in `tests/unit/monitoring/scrub.test.ts`) | `src/lib/monitoring/scrub.ts` |
| Manual capture, server: `reportError(err, { where, route, tags, extra, level })` | `src/lib/monitoring/report.ts` (`server-only`) |
| Manual capture, browser: `reportClientError(err, { where, tags, extra, level })` | `src/lib/monitoring/report.client.ts` |

**No edge config.** The Next 16 proxy runs on the Node.js runtime and no route uses the edge runtime, so only the Node.js server init exists.

**Version 11 has no `sendDefaultPii`.** `dataCollection` replaces it and collects everything by default, so `src/lib/monitoring/config.ts` switches off: user info (which also stops the IP address being inferred), cookies, headers, request/response bodies, query strings, database and queue payloads, and the local variables of stack frames (the order route holds name, phone and address in locals).

**What the scrubber does** (`beforeSend` and `beforeBreadcrumb`, on both browser and server; there is no `beforeSendTransaction` because nothing is traced; every string anywhere in an event or breadcrumb is walked, not a list of fields):

- `/staff/<anything>` becomes `/staff/[redacted]` in any letter case, also percent-encoded (URLs, transaction names, breadcrumbs, exception texts, contexts). On the server the literal values of `STAFF_PAGE_KEY`, `SESSION_SECRET`, `ADMIN_PASSWORD`, `CRON_SECRET`, `SUPABASE_SECRET_KEY`, `TELEGRAM_BOT_TOKEN`, `TURNSTILE_SECRET_KEY` and `OPENAI_API_KEY` are blanked wherever they appear as text.
- Query strings and fragments are cut from every URL (a Supabase signed upload or download link carries its token in the query). The Telegram bot token (it sits in the URL path), JWT-looking tokens and `token=` values are blanked.
- Iraqi phone numbers and PostgreSQL `Key (phone)=(...)` and `Failing row contains (...)` details in error texts are blanked.
- The `user` block (IP address included), the server host name, cookies, request headers (the staff key travels in `x-staff-key`) and request bodies are dropped. Console breadcrumbs are dropped (the order summary with the customer's name, phone and address is logged by `notifyShop`).
- A scrubber failure drops the event; it never lets an unscrubbed one through.

The tunnel does not forward cookies or custom headers, but it passes on the visitor's IP address (`X-Forwarded-For`), user agent and `Origin` / `Referer` to Sentry as transport metadata (the SDK does this on purpose: it is how Sentry tells the browser and checks the allowed domains). Events are sent with `infer_ip: never` and no `user` block, so Sentry has no reason to store the IP; as the second lock, tick "Prevent Storing of IP Addresses" in the sentry.io project settings (Settings, Security & Privacy). The staff page answers with `Referrer-Policy: no-referrer`, so its own error reports carry no `Referer`.

**Where errors are captured by hand** (they are caught, logged and answered, so `onRequestError` never sees them; the existing `console.error` stays next to each capture):

- `POST /api/orders`: the outer catch (`orders.post`), the customer upsert (`orders.customerUpsert`), and a failed shop notification (`orders.notify`, both the `notifyShop` result and a throw). Expected 4xx answers (validation, rate limit, captcha, unsupported file) are not reported.
- `POST /api/upload`, `/api/upload/direct`, `/api/upload/direct/commit`, `GET /api/cron/purge`, `POST /api/track`: the outer catch of each.
- AI designer (`src/lib/ai/*`, `/api/design/*`): OpenAI HTTP errors, timeouts and unreadable answers (`ai.openai`, `ai.brief`), an image that cannot be normalised or a custom image with no transparency (`ai.generate`), a failed release or generation record (also `ai.instructions` for the translator, and `ai.team.*` for the staff routes), the outer catch of each route, and a failed mark-ordered in `POST /api/orders` (`orders.aiMarkOrdered`). These report a fresh `Error` with a fixed message and code tags only, never the caught error and no `console.error` (a caught error or an OpenAI answer can echo the idea, the IP or the key).
- `trackServer` (`analytics.record`), `verifyTurnstile` (Cloudflare unreachable), and two places in `storage/supabase.ts`: a corrupt upload meta file, and stored settings that fail validation (a warning: prices fall back to the defaults).
- Browser: `logClient({ ... }, { report: { error } })` in `components/builder/logClient.ts` reports a thrown decode error and the degraded (WhatsApp fallback) order screen, not expected user errors; the staff page reports a failed PDF build, a failed save and a thrown decode (`staff.*`).
- Admin server actions and admin route handlers have no catch: their errors reach `onRequestError`.
- Not captured on purpose: `src/lib/storage/local.ts` and what it loads, `auth/token.ts` and `staff-gate.ts` stay free of Sentry (they run under tsx and in the proxy).

Captures carry ids, route names and error codes only (`orderId`, `uploadId`, file type and size), never a name, phone, address or file name. `reportError` flushes inside `after()` so a serverless function does not freeze before the event is sent.

**Models.** Images: `gpt-image-2.6-flare`, quality `high`, 1024 px on the long side (`AI_IMAGE_LONG_SIDE`). Brief: `gpt-5.4-mini`. OpenAI quirks are in `docs/STACK_NOTES.md`.

**Text rules** (`text-capacity.ts`). Minimum text size 12 pt (em 4.233 mm). A line of `n` characters (combining marks not counted) needs `ceil(n x 0.55 em / usable width)` rows, each `1.4 em` tall; the rows may take at most 65 % of the usable height. Usable box: circle = the inscribed square (0.70 d, less 8 %), rect = 90 % of each side, custom = 80 %. The constants were calibrated on the spike images; the unit tests pin them. Too much text for the size never blocks: `textWarning()` (`ai-logic.ts`) feeds one shared note (`TextWarningNote`) on the review box, the design step (a pending result is checked at the size it will have once accepted) and the arrangement step (the accepted design's lines, kept in the draft as `aiLines`), with the recommended size only when the size step accepts it. `generate` does not check it; `text_too_long` stays in the API contract for old clients but the server never answers it.

**Pixels** (`normaliseGenerated`). The model's opaque pixels come back at alpha 253-254 and its transparent pixels carry dark RGB, so the stored PNG is normalised: circle and rect are flattened onto white (opaque RGB; the PDF's own circle clip cuts the circle); custom keeps its alpha channel but alpha >= 250 becomes 255 and alpha <= 8 becomes 0 with white RGB. A custom result with no usable transparency is not accepted (see cost guards). The stored PNG must be at most 3.2 MB (`AI_PNG_MAX_BYTES`, re-encoded at maximum compression first) because it travels back as base64 under Vercel's 4.5 MB response limit.

**Cost guards** (what keeps the bill bounded; do not reorder `runGenerate`):

1. Everything cheap and free of OpenAI is checked first: body, the signed `briefToken` (the model's artwork description reaches `generate` from the browser, so `brief` signs it with an HMAC of `SESSION_SECRET` and `generate` refuses any description it did not sign; the raw idea is stored for the admin page but never sent to OpenAI by `generate`), the 3:1 aspect, `ai.enabled` and the key, then the in-memory limiter, then the reference images (read and prepared before the reservation, so a bad one costs nothing). Before any reference body is downloaded (only when there are references) a non-atomic read-only look (`precheckAi`: `aiListBlocks` + `aiUsage` for today; a block matches by key or by the full IP) answers `blocked` / `site_limit` / `ip_limit` exactly as the reservation would, and each reference's meta is checked through `uploadInfo` (must be png/jpeg and at most `settings.maxUploadBytes`), so a blocked or capped caller cannot make the server download and decode up to 5 files per call. The look only saves work and fails open (a read error means no opinion); the atomic reservation below still decides, and its position is unchanged.
2. Then the atomic reservation. From there on every failure gives the use back (`aiRelease`): OpenAI error, timeout, content-policy refusal, an unreadable or oversize result, a failed save. A failed try never counts against the customer.
3. **Refused but counted:** a custom shape whose image has no usable transparency was already paid for at OpenAI, so the use is **kept** and the answer is `refused` (its copy does not claim the try was free).
4. In production with `SESSION_SECRET` blank both routes answer `unavailable` (the token would be signed with a public dev salt).
5. The OpenAI call has a time budget (`maxDuration` of the route is 120 s): the route notes its start (before the body read) and `openAiTimeoutMs()` gives the call `min(AI_OPENAI_TIMEOUT_MS = 50 s, 120 s − elapsed − 20 s)`, i.e. a 110 s deadline less 10 s for normalising, saving and answering. When less than 20 s of that is left, the call is not made at all: the customer gets `failed` before anything is reserved (a second check right before the call, after the reservation, gives the use back with `aiRelease`), so a platform kill after OpenAI has charged cannot keep a use and show nothing. Retries are the customer's choice and count. A failed retry keeps the previous (paid) result on the screen, with the error above it, so «أكمل بهذا» stays available.

**Design instructions (v2).** The customer's idea may now say how the sticker should look (colours, font, where the text sits). The chain:

1. `brief` returns `instructions` (Arabic, from the model's `design_instructions`, hardened and capped by `hardenInstructions`) and `instructionsToken` = HMAC-SHA256 of `SESSION_SECRET` over `"ai-instr|" + visualDescription + "|" + instructions`. The review box shows the instructions in an editable field («تعليمات التصميم») under the printed lines.
2. `generate` takes the optional `instructions` and `instructionsToken`. No `instructions` (an old cached page, or the field was emptied) is today's path exactly. Instructions with a matching token (checked on the exact strings received) are unchanged: the signed English description is drawn and nothing extra is called. Anything else counts as edited: it is untrusted customer text.
3. Edited instructions reach OpenAI only through `translateInstructions()`, as `input` data under fixed rules, and only AFTER the atomic reservation (so the cheap checks and the limiter still come first and the order of `runGenerate` does not change). Its time budget is `translateTimeoutMs(elapsed)`: at most `AI_TRANSLATE_TIMEOUT_MS` (15 s) and never so long that less than `AI_MIN_OPENAI_BUDGET_MS` (20 s) remains for the image call after it, within the same 110 s deadline; when that comes to under `AI_TRANSLATE_MIN_MS` (5 s) it is not called. Give-back rules: no time left, a translation failure (timeout, error, incomplete answer) or an empty English result gives the use back (`aiRelease`) and answers `failed`; a content-policy refusal of the translation gives it back and answers `refused`. The English result goes through `hardenVisualDescription` like the brief's.
4. The image prompt wrapper: with a translated description the template says the artwork text is design instructions written by the customer and must never be written on the sticker, and a closing rule says the shape, size, exact lines and text size win over anything in the description (the printed lines are still the confirmed `lines`, never the instructions).
5. The record keeps the Arabic instructions as confirmed (`AiGenerationRecord.instructions`, null when there were none; the gallery search also reads it). The raw idea is still stored and never sent to OpenAI by `generate`.

**The actor seam.** `runBrief(request, json, actor)` and `runGenerate(request, json, clock, startedAt, actor)` take an `AiActor` (a strategy object in `service.ts`) that decides who is asking and under which limits: `identify(request)` (the full IP and the usage key), `briefKind` / `imageKind`, `limits(settings)`, `limiterKey(ip)`, `guard` (which in-memory limiters) and `staffId`. The default, `customerActor`, is the behaviour before v2 (per-IP key from `aiIpKey`, over the /64 for an IPv6 address, kinds `brief` / `image`, the admin's per-IP and site limits, `limiters().brief` / `.generate`); the customer routes pass nothing. `staffActor(staffId)` identifies by the account: `ip` is always '' (no staff IP is stored, and an admin block on the shop's IP, which matches by full IP, never stops staff), the usage key is `staff:<id>`, the kinds are `staff_brief` / `staff_image`, the limits are the staff constants above, and the generation record carries `staffId`. `reserve_ai` / `release_ai` are reused unchanged; only the `kind` check of `ai_usage` was widened by the migration.

**Staff designer (`/team`).** For the shop's own staff, with their own accounts (admin page `/admin/staff`; session in "Admin protection", above). `TeamDesigner` (`src/components/team/`) runs the same `useAiDesign` hook as the builder, pointed at the staff endpoints (`TEAM_AI_ENDPOINTS`: `/api/team/design/*` and `/api/team/upload*` for the reference images), and the same `AiProgress`. The hook takes a `host` (the subset of the builder API it uses, `AiHost`) and optional `endpoints`; `Builder.tsx` satisfies `AiHost` structurally and is unchanged. The result is a preview, «نزّل التصميم PNG», retry and new design: staff do not place orders from it. Each design is stored like a customer's (an ordinary upload plus an `ai_generations` row) and shows in `/admin/designs` with the staff badge; the 50-a-day count is read from `ai_usage` (kind `staff_image`) by the page and by `/admin/staff`. If the staff migration is not applied, the storage staff methods throw a typed `not_ready` (`src/lib/storage/staff-errors.ts`, no imports, loaded by `local.ts`) or are missing, and the login, `currentStaff()` and `/admin/staff` all fail closed with their "not ready" notice; customers are unaffected, and the Supabase adapter retries a generation insert without `instructions` / `staff_id` when PostgREST reports an unknown column.

**Progress bar (v2).** The routes answer one JSON at the end, so progress is estimated. `src/components/builder/ai/progress-logic.ts` (pure) maps elapsed milliseconds to `{ percent, stageIndex, slow }`: asymptotic, always under 95 % until the answer arrives, never still. `AiProgress.tsx` (`{ kind: 'brief' | 'image', startedAt?, className? }`) draws it with `role="progressbar"`, the stage text in a polite live region that changes only when the stage changes (the percentage is not announced) and `prefers-reduced-motion` respected. `startedAt` lets the start survive a remount. It is used for the brief wait (`StartStep`), the image wait (`AiResult`) and the staff page.

**After generation.** The PNG is saved as an ordinary upload (`uploads/<id>.bin|json`, original name `ai-design.png`) and recorded in `ai_generations` (full IP, `ip_key`, shape, size, idea, printed lines, `uploadId`, `orderId: null`). Recording is tried twice; if both fail the customer still gets the design and only the gallery entry is lost (that upload is then unreferenced and follows the unused-upload rule). `POST /api/orders` calls `aiMarkOrdered(uploadId, orderId)` after saving the order (best effort, never fails the order), which fills `orderId` and makes the gallery link to the order.

**Admin.** `/admin/designs`, `/admin/staff` and the image route (section 1). The «إلغاء الحظر» and «احظر» buttons stop generation only; a blocked customer can still upload a design and order. Settings: the three `ai` fields in `/admin/settings`.

## 7. Tests

- **Pure library code**: a `*.test.ts` file next to the module (`src/lib/pricing.test.ts`, `src/lib/layout/layout.test.ts`).
- **Anything that needs fixtures, environment variables, a mocked `fetch` or a route handler**: `tests/unit/<area>/` (`server`, `builder`, `admin`, `analytics`, `design`, `pdf`, `pages`, `components`).
- **`tests/unit/golden/`**: the behaviour oracle. It pins what the code does today: every Arabic string, layout results, PDF content hashes, API status codes and bodies, stored JSON, exact Supabase requests. A failing golden test means behaviour changed. Fix the code. Update a snapshot only for a change the owner asked for, one file at a time (`pnpm exec vitest run <file> -u`), and read the snapshot diff line by line.
- **`tests/e2e/`**: Playwright against `next dev` on port 3199 with `./data-e2e`. Run the whole suite: the admin spec uses the order that the order-flow spec creates. `staff.spec.ts` opens the hidden staff page with the test key from `playwright.config.ts`, adds two designs, downloads the two files (one per design) and checks that each has 1 page with the `sk_marks` dots, the file names and the privacy headers; a wrong key is a 404 identical to `/nonexistent-page` (`next dev` echoes each 404's own URL in the flight data, so the test removes that echo before comparing). `data-e2e/settings.json` is gitignored and local only: if an older copy has `layout.marginUm` at 7000, `admin.spec.ts` fails on the margin round-trip; delete the file so the defaults (3 mm) apply.

React `cache()` only memoises inside a server render, so under vitest `getSettings()` reads storage on every call and no unit test can see the memoisation; the rule "writers read through `getStorage().getSettings()`" is kept by review, not by a test.

`pnpm check` runs typecheck, unit tests, lint and the RTL lint. In CI or before a release run the tests with `CI=1`, so a missing snapshot fails instead of being written.

## 8. How to

**Add or change a visible string**

1. Edit the right file in `src/content/ar/` (`common`, `builder`, `order`, `pages`, `admin`). Placeholders are `{name}`.
2. Use it through `import { builder, fill } from '@/content/ar'`. Wrap numbers, units and ids in `<Ltr>`, or use `fillLtr` / `<Money>`. Never write Arabic or English text in a component.
3. `pnpm check`. The copy golden test fails on purpose. Update only that snapshot (`pnpm exec vitest run tests/unit/golden/copy.golden.test.ts -u`) and check that its diff shows your string and nothing else. A string that another golden file also prints (order text, Telegram caption, API error messages, page metadata) makes that snapshot fail too: update it the same way, one file at a time.

**Add a setting the owner can edit**

1. `src/lib/types.ts`: add the field to `ShopSettings` (or a nested type).
2. `src/config/defaults.ts`: add its value to `DEFAULT_SETTINGS`. Stored settings are merged over the defaults, so existing data keeps working.
3. `src/lib/storage/settings-schema.ts`: add it to `shopSettingsSchema`. A limit that the form also needs goes in `settings-limits.ts`.
4. `src/app/admin/settings/SettingsForm.tsx` (the input) and `parse-form.ts` (reading it). A layout distance typed in millimetres goes in `fields.ts` instead.
5. `src/content/ar/admin.ts`: the label, under `admin.settings`.
6. Tests: `tests/unit/admin/settings-form.test.ts`. The settings and copy golden snapshots change; update them deliberately.

**Add a Supabase migration**

1. Create a new file `supabase/migrations/<YYYYMMDDHHMMSS>_<name>.sql`. Never edit a file that has been applied: the database has already run it.
2. Turn row level security on for a new table and add no policies.
3. Mirror the behaviour in `src/lib/storage/local.ts`, and extend `StorageAdapter` in `types.ts` if a method is new, so development and tests behave like production.
4. Add tests for both adapters (`tests/unit/server/storage*.test.ts`, `supabase-storage.test.ts`).
5. Apply the migration to the Supabase project before deploying the code that needs it.

**Accessibility conventions of the builder** (`tests/unit/components/a11y-markup.test.ts` pins them)

- Live regions (`role="status"`) are always mounted and empty when idle (`DesignStep` loading, `DetailsStep` `#submit-status`); they name a phase and never carry a percent. The visible progress block is not a live region and the progress bar is named by `#submit-status` (`aria-labelledby`).
- After a file has been read, `DesignStep` moves focus to the replace button (or the drop zone on failure) only when focus fell to `<body>`.
- The hand-made shape radio group keeps `role="radio"` (the e2e helper `chooseShape` needs it): roving `tabIndex` and arrow keys through `src/components/builder/radio-nav.ts` (RTL: Left/Down next, Right/Up previous).
- Hidden file inputs are `aria-hidden` + `tabIndex={-1}`; the visible button is the control. The required delivery fields carry `aria-required` (the form stays `noValidate`).
- `html { scroll-padding-top: var(--header-h) }` keeps focused and anchored elements below the sticky header; do not add `scroll-mt-*` for the header on top of it.

## 9. Hard invariants

Breaking one of these loses data, breaks a customer in the middle of an order, or changes what gets printed. Each needs an explicit decision by the owner.

1. **Applied migrations** in `supabase/migrations/` are never edited, including their old-brand header comments.
2. **Stored JSON shapes**: `OrderRecord`, `ShopSettings`, `CustomerRecord`, `AnalyticsEvent`, `StoredFileMeta`. Add fields as optional or with a default; never rename or remove one. Orders saved before per-sheet pricing have another `price` shape and must keep rendering (`order-price-view.ts`).
3. **Bucket and paths**: the bucket `etihad` and the keys `uploads/<id>.bin`, `uploads/<id>.json`, `orders/<id>.pdf`.
4. **PDF bytes and geometry**: the layout engine (`src/lib/layout`, fixtures in `src/lib/__fixtures__/layout-cases.json`) and the drawing code (`build-sheet.ts`, `sheet-page.ts`, `build-staff-pdf.ts`) decide what is printed. Their output is pinned by fixtures and golden hashes; an "equivalent" rewrite that changes one byte or one micrometre is a behaviour change.
5. **Visible copy**: every string in `src/content/ar`, the order summary text and the Telegram caption.
6. **Old-brand identifiers that are data.** They look like leftovers of the previous shop name but they are stored in browsers, databases or URLs: the bucket `etihad`, the cookies `ep_admin` and `sf_staff` (the staff designer session), the order number prefix `EP-`, the browser storage keys `ub:form:v1` (sessionStorage), `ub:draft:v1` (localStorage), the IndexedDB database `ub:draft`, `ub:order-success:v1`, `ub:order-attempt:v1` (sessionStorage; multi-design orders add an optional `extraUploads`), `ub:order-note:v1:<displayNo>` (sessionStorage, the success popup shown once), the IndexedDB keys `design:<fileId>` of extra designs in `ub:draft`, `softy-tracked`, `softy-step-<id>` and `softy-install-dismissed`, the `globalThis` keys `__epStorage` and `__epLimiters`, the package name `etihad`, and every environment variable name.
7. **API surface**: route paths, status codes, the JSON bodies and their key order.
8. **Security boundaries**: the session check stays the first statement of every admin page behind the login, of `updateOrderStatus` and `saveSettingsAction`, and of every `/api/admin` route handler (`adminApiGuard()`: `customers`, `files/<orderId>/<pdf|design>` and `designs/<uploadId>/image`; see section 1); likewise `await requireStaff()` is the first statement of every `/team` page behind the login and `staffApiGuard()` of every `/api/team/*` handler, and the `/admin/staff` actions start with `requireAdmin()` (`/team` has no proxy coverage, so these guards are the only protection); server modules keep `import 'server-only'`; the price is always recomputed on the server; no IP or user agent is added to a stored analytics event (the three AI tables are the one decided exception, invariant 13); the OpenAI key stays server-side and `/api/design/*` never call OpenAI before the limits and checks of the AI section.
9. **The visitor hash inputs** (section 5). `ipOf()` in `analytics/server.ts` and `clientIp()` in `rate-limit.ts` are separate on purpose: merging them changes stored hashes.
10. **The dots geometry** (`REG_MARKS`: 5 mm wide, centre 7 mm from both edges, 3 mm clearance, K black, layer `sk_marks`) matches the plotter's template. A dot at 6.8 mm or 4.8 mm wide may be rejected by the machine, and a sticker within 3 mm of a dot may make the camera misread the sheet. Change it only on the owner's word after a plotter test. The same goes for `PrintScaling /None`: a sheet shrunk by "fit to page" moves the dots off the template.
11. **The staff key never leaks**: `/staff` stays out of the sitemap, `robots.txt` and analytics, the staff page sends no design file to the server, and a wrong key gets exactly the answer of an unknown URL (so no route may match `/staff/<anything>`; the page stays behind the proxy rewrite).
12. **Nothing private goes to Sentry**: never the staff key or any `/staff/<key>` URL, never customer data (name, phone, address, file names or contents, and in the AI designer the idea text, the printed lines, the IP, the OpenAI key and OpenAI response bodies), never a signed URL with its token, a bot token or a cookie. Keep `dataCollection` in `src/lib/monitoring/config.ts` switched off (this SDK version has no `sendDefaultPii`; `dataCollection` is its replacement), keep every `Sentry.init` behind the scrubber hooks, and pass only ids and codes to `reportError` / `reportClientError`. Do not add tracing, replay or profiling.
13. **The AI tables and RPCs** (migration `20261121000000_ai_designer.sql`, applied once it reaches production: never edit it, add a new file): `ai_usage`, `ai_generations` (`upload_id` unique), `ai_blocks`, and the RPCs `reserve_ai` / `release_ai`. RLS on, no policies, nothing granted to `anon` or `authenticated`, the RPCs `security invoker` and executable by `service_role` only. `reserve_ai` is the only thing that makes the daily limits atomic across serverless instances (advisory lock per day and kind, order: blocked by `ip_key` or full IP, site cap, per-IP cap); do not replace it with read-then-write. These tables hold the full client IP (D9); that is allowed for them only, and `AiGenerationRecord`, `AiUsageRow` and `AiBlock` follow invariant 2. `ShopSettings.ai` is the new settings key (appended after `retentionDays`: key order is golden-pinned).
14. **The AI adapter methods are optional on `StorageAdapter`** (`aiReserve`, `aiRelease`, `aiRecordGeneration`, `aiMarkOrdered`, `aiListGenerations`, `aiUsage`, `aiBlock`, `aiUnblock`, `aiListBlocks`, `aiPurgeUsageBefore`, and since 2026-11-26 `aiGetGeneration`, `aiDeleteGeneration`, `orderUsingUpload`, `aiPurgeUnordered`, `purgeUnusedUploads`) so a third adapter or a test double compiles without them; both real adapters implement all of them. `service.ts` answers `unavailable` when `aiReserve` or `aiRelease` is missing, and the order route and the admin pages use `?.`: a missing method must never break an order. `local.ts` keeps its no-`server-only`, relative-import rule (section 3) for its AI code too.
15. **Builder steps keep their ids** (`shape`, `design`, `size`, `quantity`, `details`, `STEPS` in `types.ts`). They are data: analytics `step` events, the admin funnel, draft restore and `builder-logic.golden`. The AI designer changed what the `shape` and `design` steps render and their stepper labels, not their ids or order. An accepted AI design enters through the same `onFile()` as an upload, and the submit flow reuses its `uploadId` instead of uploading the PNG again; the order, the PDF and the staff sheet for an uploaded design are unchanged.
16. **Retention rules** (D10, section 5; changed 2026-11-26): orders and the design files they used are kept forever; only `orders/<id>.pdf` is purged after `retentionDays`; **designs no order used are deleted 7 days after they were made** (`UNORDERED_DESIGN_DAYS`; `aiPurgeUnordered` then `purgeUnusedUploads` in the cron, both refuse a cutoff newer than 7 days, both read every order that could use an upload BEFORE deleting and delete nothing when a read fails; a used design is healed, never deleted; deletes go by explicit id/path lists only); `purgeOlderThan` never deletes an upload that an order or an `ai_generations` row uses; orders created before `KEEP_DESIGNS_FROM` keep the old delete-everything rule, with no lower bound on their age (nothing promised is stranded by an outage). Moving `KEEP_DESIGNS_FROM` earlier would keep data that customers were told would be deleted; moving it later would delete data that is now meant to stay, which is worse. Set it once, to the deploy instant or slightly earlier, never later. A purged PDF must stay a handled state in the admin (410 and the `admin.orders.pdfPurged` text), never a 500.
17. **The deletion promise is gone from the copy** (D11): `builder.details.consent` and `common.filesNotice` no longer promise that design files are deleted. Do not put such a sentence back unless the retention rule above changes first. NOTE (2026-11-26): the rule HAS changed for designs no order used (deleted after 7 days, invariant 16), so whether the copy should now say so is an owner decision; until then the copy is silent about it.
18. **The staff designer table, columns and cookie** (migration `20261126000000_staff_designer.sql`, applied once it reaches production: never edit it, add a new file): `staff_accounts` (RLS on, no policies, everything revoked from `anon` and `authenticated`, reached only with the secret key), the widened `ai_usage_kind_check` (`image`, `brief`, `staff_image`, `staff_brief`), and the columns `ai_generations.instructions` and `ai_generations.staff_id` (no foreign key: accounts are never hard-deleted, only disabled, so old generations stay valid). `StaffAccountRecord`, `AiGenerationRecord.instructions` / `staffId` and the `staff_*` usage kinds follow invariant 2 (add, never rename or remove). The session cookie name `sf_staff`, the usage key format `staff:<id>` and the password format `scrypt$N$r$p$saltB64$hashB64` are stored data: changing one logs staff out or locks them out (a format change must keep verifying old hashes). The staff storage methods (`staffList`, `staffGet`, `staffByPhone`, `staffCreate`, `staffUpdate`, `staffTouchLogin`) are optional on `StorageAdapter` like invariant 14's, and they fail closed: a missing method or a `not_ready` error must never break the customer flow or an order. Until the migration is applied the customer designer keeps working (the generation insert is retried without the two new columns).
19. **`/team` stays private and unproxied by design (R3).** `/team` and `/api/team` are out of the sitemap, disallowed in `robots.txt` and ignored by analytics (`isTeamPath`, part of `isStaffPath`; `Tracker`, `InstallPrompt` and `/api/track` use it), and the pages are `noindex`. Do NOT extend `src/proxy.ts` or its pinned matcher for them: its `staffGate` swallows every path that starts with `/staff`, and invariant 11 depends on it staying exactly as it is. A staff generation never touches the customer limits (separate usage kinds), never stores an IP, and is never counted in the admin's customer tiles.
20. **Meta never sees private paths or customer details** (section "Meta Pixel and Conversions API"): `isMetaExcludedPath` keeps Meta's script and every event off `/admin`, `/staff`, `/staff-sheets` and `/team` in any letter case, `fbq.disablePushState` and `autoConfig: false` stay set, and the Conversions API sends the phone and country only as SHA-256 hashes and never the name, address, notes or file. Every Meta call stays best effort: it must never fail or delay an order.
